# User model
```js
import mongoose ,{Schema, model,models} from 'mongoose';
import bcrypt from 'bcryptjs';

export interface IUser {
    email: string;
    password: string;
    _id?: mongoose.Types.ObjectId;
    createdAt?: Date;
    updatedAt?: Date;
}

const userSchema = new Schema<IUser>(
    {
        email: {
            type: String,
            required: true,
            unique: true,
        },
        password: {
            type: String,
            required: true,
        },
    },
    {
        timestamps: true,
    }
    );

userSchema.pre('save', async function (next) {
    if(this.isModified('password')) {
        this.password = await bcrypt.hash(this.password, 10);
    }
    next()
})

const User =models?.User || model<IUser>('User', userSchema);
```

### 1. Why did we create the interface first?

```ts
export interface IUser {
  email: string
  password: string
  _id?: mongoose.Types.ObjectId
  createdAt?: Date
  updatedAt?: Date
}
```

Reason:
This is just a blueprint for TypeScript.
It says:
* Every user **must have** `email` and `password`.
* User **may have** `_id`, `createdAt`, `updatedAt` (added by MongoDB later).

This helps TypeScript give you:

* Autocomplete when you type `user.`
* Errors if you try to use a field that doesn’t exist like `user.age`.

So **interface = a checklist for what a User object looks like.**
In plain JavaScript, this is not needed.
### 2. Why did we create userSchema?

```ts
const userSchema = new Schema<IUser>(...)
```

Reason:
This is the actual MongoDB **schema**.
It tells Mongoose how to save a User document in MongoDB.

It defines:
* `email` → type String, required, unique
* `password` → type String, required
* Adds `createdAt` and `updatedAt` automatically with `timestamps: true`

This is what MongoDB will use to create the collection and validate data.
### 3. Why did we hash the password?

```ts
userSchema.pre('save', async function (next) {
  if (this.isModified('password')) {
    this.password = await bcrypt.hash(this.password, 10)
  }
  next()
})
```

Reason:
To make sure the password is stored securely.

Steps:
* Before saving a user (`pre('save')`), check if the password was changed.
* If yes, hash the plain password using bcrypt.
* Replace the plain password with the hashed one.
* Call `next()` so Mongoose can continue saving.

Without this step, passwords would be saved in plain text.
### 4. Why did we create the User variable with IUser?

```ts
const User = models?.User || model<IUser>('User', userSchema)
```

Reason:

* `models?.User` checks if a User model already exists (useful during development with hot reload).
* If it doesn’t exist, `model<IUser>('User', userSchema)` creates a new User model from the schema.

The `<IUser>` here again links the User model to the IUser interface for type safety.
This ensures:

* `User.findOne()` returns an object matching IUser.
* You get type checking and autocomplete.

In plain JavaScript, it would simply be:

```js
const User = models.User || model('User', userSchema)
```
### Summary of flow

| Step                | Why?                                       |
| ------------------- | ------------------------------------------ |
| Create `IUser`      | Blueprint for TypeScript (not MongoDB).    |
| Create `userSchema` | Define User shape for MongoDB.             |
| Add `pre('save')`   | Hash password before saving.               |
| Create `User` model | Combine schema and interface into a model. |

# EXTRA THEORY
#### 🗝 Why `_id` in `IUser`?

* **MongoDB auto-generates `_id`** for every document as a unique identifier.
* When **creating** a user → `_id` is not required (MongoDB adds it).
* When **fetching** a user → `_id` is present in the returned data.
* Adding `_id?: ...` to `IUser` tells TypeScript:

  > "*id might exist because MongoDB provides it, but it’s optional when creating a new user.*"
##### ✅ Without `_id`

TypeScript throws an error when you use `user._id` because it doesn’t know it exists.
#### 📦 Example
```ts
export interface IUser {
    email: string;
    password: string;
    _id?: mongoose.Types.ObjectId
}
```
#### 🔥 Key Takeaways

| Action        | Why `_id`?               |
| ------------- | ------------------------ |
| Create User   | MongoDB generates `_id`. |
| Fetch User    | MongoDB returns `_id`.   |
| Type Checking | TypeScript needs `_id`.  |

## Iuser 

Good question. Let’s break this down very simply so you fully get it.

---
### What’s special about `IUser`?

**Short answer:**
`IUser` is **not special for MongoDB or Mongoose**. It is only for **TypeScript**.
It is like a **blueprint** that tells TypeScript what a User object should look like.

In your code:

```ts
export interface IUser {
  email: string
  password: string
  _id?: mongoose.Types.ObjectId
  createdAt?: Date
  updatedAt?: Date
}
```

This says:

* Every User must have an `email` (string)
* Every User must have a `password` (string)
* A User **may** have `_id`, `createdAt`, and `updatedAt` (optional because MongoDB adds them later)

TypeScript uses this to:

* Catch mistakes when coding
* Give autocomplete in your editor
* Prevent using wrong properties like `user.age` (which doesn’t exist)

---

### Is `IUser` needed for Mongoose?

No. Mongoose doesn’t care about `IUser`.
Mongoose only needs the schema:

```ts
const userSchema = new Schema({ ... })
```

and the model:

```ts
const User = model('User', userSchema)
```

---

### So what’s special about it?

Only TypeScript cares about it.
It helps you write safer code, but it doesn’t change how MongoDB or Mongoose work.

---

### Without TypeScript (JavaScript version)

You don’t need `IUser` at all.
You directly use the schema and model.

---

### Why do people use `IUser` in TS?

Because it lets them define:

* What fields a User has
* What type each field is (string, Date, ObjectId, etc.)
* Optional fields with `?`

This keeps their code **type-safe** and avoids runtime bugs.

---
### 1. What happens if you don’t use `IUser` in TypeScript?

#### Your code without `IUser`:

```ts
const userSchema = new Schema({
  email: String,
  password: String
})

const User = model('User', userSchema)
```

Now when you fetch a user:

```ts
const user = await User.findOne({ email: 'test@gmail.com' })
console.log(user.email)
console.log(user._id)
```

#### Problem:

TypeScript does not know what `user` looks like.  
It will say:

```
Property 'email' does not exist on type 'Document<any, any, any>'
```

TypeScript thinks `user` could be **anything** because we didn’t give it a type.

---

#### With `IUser`

You wrote:

```ts
export interface IUser {
  email: string
  password: string
  _id?: mongoose.Types.ObjectId
}
```

Then connected it to the schema and model:

```ts
const userSchema = new Schema<IUser>({...})
const User = model<IUser>('User', userSchema)
```

Now when you fetch:

```ts
const user = await User.findOne({ email: 'test@gmail.com' })
```

TypeScript knows:

- `user.email` is a string
    
- `user.password` is a string
    
- `user._id` might be an ObjectId
    

Your editor gives autocomplete and warnings if you try something invalid like:

```ts
console.log(user.age) // ❌ Property 'age' does not exist
```

---

### 2. Why `IUser` is completely unnecessary in JavaScript

In JavaScript, there is no TypeScript type checking.  
You can write:

```js
const user = await User.findOne({ email: 'test@gmail.com' })
console.log(user.email)
console.log(user._id)
console.log(user.age) // No error, even though age doesn't exist
```

There won’t be any error at coding time because JavaScript doesn’t check types.

But this means:  
If you make a mistake (like accessing `user.age`), you won’t know until the code runs and crashes.

That’s why in TypeScript we use `IUser`—to **catch these mistakes before running the code.**

---

### Key Difference

|Feature|With IUser (TypeScript)|Without IUser (JavaScript)|
|---|---|---|
|Autocomplete|Yes|No|
|Type error on wrong prop|Yes|No|
|Safer code|Yes|No|

---
### Summary
- `IUser` is for **TypeScript only**. It connects your model to a strict blueprint for safer code.
- In JavaScript, you don’t use it because there’s no type checking. You just write schema and model directly.
