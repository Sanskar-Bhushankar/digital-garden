# Explanation of code

### First: What is this `types.d.ts` storing?

```ts
declare global {
    var mongoose: {
        conn: Connection | null
        promise: Promise<Connection> | null
    }
}
```

This is creating a **global variable** in Node.js called `global.mongoose`.

It has two properties:

* `conn`: stores the **active MongoDB connection** (if one exists).
* `promise`: stores a **promise** that resolves when MongoDB finishes connecting.

So basically:

| Field     | What it stores                                                 |
| --------- | -------------------------------------------------------------- |
| `conn`    | A live MongoDB connection (or null if not connected).          |
| `promise` | A promise that represents “connecting to MongoDB” in progress. |

---

### Why store these?

In development (like Next.js), **hot reload** causes the server to restart and reload files.
Every reload will run `connectToDatabase()` again.

Without `global.mongoose`:
Each reload would create a **new MongoDB connection** → leading to this error:

```
MongoServerError: Too many connections
```

By using `global.mongoose`, we check:

> “Do we already have a connection or one in progress?”

* Yes → reuse it.
* No → create a new one and store it.

So even when the app reloads, the connection stays cached in memory.

---

### But how is the connection maintained across reloads?

In Node.js, the `global` object **persists between module reloads** during hot reload.

So if you do:

```ts
global.mongoose = { conn, promise }
```

That stays in memory, even if your code reloads.

Your next API call will reuse this cached connection because `global.mongoose.conn` is still there.

This avoids sending **multiple connect requests** to MongoDB.

---

### You asked: If it's storing, then don't I still send a request for every API call?

No.

* On first API call → `mongoose.connect()` runs → connection established → cached.
* On next API calls → your code checks `if (cached.conn)` → it **finds the cached connection** and reuses it.

So only **queries** (like `find()`, `insertOne()`) go over the connection.
The expensive step of "establishing a new connection" does not happen again.

---

### What is maxPoolSize?

In your code:

```ts
const opts = {
  maxPoolSize: 10
}
```

This sets the **connection pool size**.

MongoDB uses a **pool of sockets** for a single connection.

* **Pool size** = number of clients that can send queries at the same time.
* Example: If `maxPoolSize = 10`, up to 10 operations can happen in parallel over that one connection.

Why?
This avoids opening new TCP connections for every query, which is slow.

---

### What is polling in DB?

Polling = repeatedly checking for changes in the database at a fixed interval.
For example:

* Every 5 seconds, check if new documents were added.

This is used when your app needs to "watch" changes without using real-time features like change streams.

But in your case, there’s no explicit polling happening.

---

### Re-explaining `connectToDatabase` step by step

```ts
export async function connectToDatabase() {
  if (cached.conn) {
    return cached.conn
  }
  if (!cached.promise) {
    const opts = { bufferCommands: true, maxPoolSize: 10 }
    cached.promise = mongoose.connect(MONGODB_URI, opts).then(() => mongoose.connection)
  }
  try {
    cached.conn = await cached.promise
  } catch (err) {
    cached.promise = null
    throw err
  }
  return cached.conn
}
```

Step by step:

1. **Check if already connected**

```ts
if (cached.conn) return cached.conn
```

If we already have a connection, return it immediately.

2. **If not connected, check if a connection is in progress**

```ts
if (!cached.promise) { ... }
```

If no promise exists, start connecting.
Save the promise so other calls can wait for the same connection.

3. **Connect to MongoDB**

```ts
cached.promise = mongoose.connect(MONGODB_URI, opts).then(() => mongoose.connection)
```

Start the connection. Options include:

* `bufferCommands: true` → queue MongoDB operations until connected.
* `maxPoolSize: 10` → up to 10 parallel queries.

4. **Wait for connection to finish**

```ts
cached.conn = await cached.promise
```

Wait until the promise resolves and store the actual connection.

5. **Error handling**
   If connection fails, clear `cached.promise` so we can retry later.

6. **Return the connection**
   Return `cached.conn` so your app can send queries over it.

---

### Why do we need both `conn` and `promise`?

* `conn`: Stores the finished connection.
* `promise`: Stores the "in-progress" connection while it’s still connecting.

This way, if multiple API requests hit at the same time, they don’t all call `mongoose.connect()`. They wait for the same promise.

---

### Summary of the whole flow

| Step                     | What it does                              |
| ------------------------ | ----------------------------------------- |
| Check `cached.conn`      | Reuse active connection if exists.        |
| Check `cached.promise`   | Wait for in-progress connection if any.   |
| Start `mongoose.connect` | Connect only if no connection or promise. |
| Save to `cached.conn`    | Store active connection for reuse.        |
| Return `cached.conn`     | Give the connection to your app.          |
